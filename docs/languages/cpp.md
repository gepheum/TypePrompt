# C++ Integration Guide

This guide explains how to use TypePrompt-generated C++ code in your application.

---

## Installation & Setup

TypePrompt generates a clean, standalone, header-only C++ library that relies exclusively on the standard library with zero third-party dependencies.

- **Standard**: C++20 or later (`-std=c++20` or `-std=c++23`)
- **Dependencies**: None (Standard Library only)

In your `typeprompt.json` configuration file, specify your C++ output file path and optional root namespace (defaults to `typeprompt`):

```json
{
  "gen": {
    "cpp": {
      "file": "include/gen/prompts.h"
    }
  }
}
```

Or in `typeprompt.yml`:

```yaml
gen:
  cpp:
    file: include/gen/prompts.h
```

Generate the C++ code:

```bash
npx typeprompt gen
```

---

## Quick Start

Include the generated header and call `Render<Template>` with designated initializers for typed input:

```cpp
#include "gen/prompts.h"
#include <iostream>

using namespace typeprompt;

int main() {
  auto prompt = Render<templates::Translate>({
      .target_language = "French",
      .text = "Hello world",
  });

  std::cout << "System prompt:\n" << prompt.system_message << "\n\n";
  std::cout << "User prompt:\n"   << prompt.user_message   << "\n";
  return 0;
}
```

---

## The `Prompt` Object

Calling `Render<Template>()` returns a `Prompt` struct containing everything needed to execute the LLM request:

| Field | Type | Description |
|---|---|---|
| `prompt.system_message` | `std::string` | Resolved system prompt text. |
| `prompt.user_message` | `std::string` | Resolved user prompt text. |
| `prompt.meta` | `schema::meta::Meta` | Typed metadata defined in the template (e.g., `model`, `temperature`). |
| `prompt.examples` | `std::vector<FewShotExample>` | List of few-shot examples (`FewShotExample`), if defined. |
| `prompt.tools` | `std::map<std::string, Tool>` | Available tool definitions and their input JSON schemas. |
| `prompt.output_format` | `OutputFormat` | Format descriptor (`OutputFormat::kJson` or `OutputFormat::kText`). |
| `prompt.output_json_schema` | `std::optional<JsonNode>` | JSON Schema for structured output validation when format is JSON. |
| `prompt.template_id` | `std::string` | Template identifier string (e.g. `"Main:Translate"`). |

## Error Handling with `Result<T>`

Code generated by TypePrompt does not throw exceptions. Fallible operations return a value-based `Result<T>`:

```cpp
template <typename T>
class Result {
 public:
  constexpr bool ok() const;                    // true if operation succeeded
  constexpr const T& operator*() const&;        // access value (precondition: ok() == true)
  constexpr const T* operator->() const;        // member access
  const Error& error() const&;                  // access error (precondition: ok() == false)
};
```

An `Error` provides a human-readable diagnostic message:

```cpp
struct Error {
  std::string message;
};
```

## Parsing LLM Responses

Pass the LLM's response string to `ParseResponse<Template>()` to validate and parse it into your strongly-typed output:

```cpp
using Template = templates::TriageTicket;

std::string_view raw_model_output = /* response from LLM */;

Result<typename Template::output_type> result =
    ParseResponse<Template>(raw_model_output);

if (result.ok()) {
  std::cout << "Category: " << result->summary << "\n";
  if (result->suggested_reply.has_value()) {
    std::cout << "Reply: " << *result->suggested_reply << "\n";
  }
} else {
  std::cerr << "Validation failed: " << result.error().message << "\n";
}
```

- **JSON Outputs**: Automatically strips markdown code fences (`` ```json ... ``` `` or `` ``` ... ``` ``) and parses the JSON into strongly-typed C++ structs, enums, variants, and vectors.
- **Text Outputs**: Returns `std::string` directly.

## Executing Tools

When a template registers `<tools>`, implement a typed tool executor and construct a `ToolExecutor` using `MakeToolExecutor<Template>()`.

### 1. Implement the Typed Tool Executor

Define a functor struct with an overloaded `operator()` for each tool registered in the template:

```cpp
#include "gen/prompts.h"

using namespace typeprompt;

struct ResearchExecutor {
  // Define an operator() overload for each tool declared in the template:

  Result<schema::web_search::Output> operator()(
      tools::WebSearch,
      const schema::web_search::Input& input) {
    const std::string& query = input.query;

    // Call your search service
    auto search_results = RunWebSearch(query);

    schema::web_search::Output output;
    for (const auto& item : search_results) {
      output.results.push_back({
          .snippet = item.snippet,
          .title = item.title,
          .url = item.url,
      });
    }
    return output;
  }
};
```

### 2. Dispatch Tool Calls

Bind your executor to the template with `MakeToolExecutor<Template>()`:

```cpp
using Template = templates::ResearchQuestion;

ResearchExecutor typed_executor;
std::unique_ptr<ToolExecutor> tool_executor =
    MakeToolExecutor<Template>(&typed_executor);

// Incoming tool call from LLM response:
ToolCall call{
    .call_id = "call_123",
    .tool_name = "webSearch",
    .stringified_input = R"({"query": "TypePrompt C++"})",
};

ToolCallResponse response = tool_executor->Execute(call);

std::cout << "Call ID: " << response.call_id << "\n";
std::cout << "Output:  " << response.stringified_output << "\n";

if (response.error.has_value()) {
  std::cerr << "Tool error: " << *response.error << "\n";
}
```

#### Smart Pointer & Lifetime Support
`MakeToolExecutor<Template>()` accepts raw pointers (`&executor`), `std::shared_ptr`, and `std::unique_ptr`:

```cpp
auto executor = MakeToolExecutor<Template>(std::make_unique<ResearchExecutor>());
```

#### Templates Without Tools
For templates with no tools, you can call `MakeToolExecutor<Template>()` with no argument. The tool executor will reject all tool calls with a `"Tool not found"` error:

```cpp
auto no_tools_executor = MakeToolExecutor<templates::Translate>();
```

### 3. ToolCallResponse Format & Provider Integration

The `ToolCallResponse` contains:
- `stringified_output`: On success, the JSON serialization of your tool's output struct. On error, a JSON error object (`{"error": "..."}`).
- `error`: An `std::optional<std::string>` containing the error message if input parsing, schema validation, tool execution, or tool lookup failed.

**Integration guidelines:**
- **OpenAI / Gemini APIs**: Send `response.stringified_output` directly as the tool message content.
- **Anthropic API**: Check if `response.error.has_value()`. If present, set `is_error: true` and pass `*response.error` as content; otherwise pass `response.stringified_output`.

## Type Definitions and `schema`

All types declared in your TypePrompt schemas are generated in the `schema` namespace:

```cpp
// Template inputs & outputs
using TriageInput = schema::triage_ticket::Input;
using TriageOutput = schema::triage_ticket::Output;
using TicketCategory = schema::triage_ticket::TicketCategory;

// Tool inputs & outputs
using SearchInput = schema::web_search::Input;
using SearchOutput = schema::web_search::Output;

// Metadata type
using Meta = schema::meta::Meta;
```

### Constructing Structs & `::whole`

TypePrompt generates an inner `struct whole` builder for every interface struct. Using `::whole` forces you to set all the fields of the struct at construction:

```cpp
using TriageInput = schema::triage_ticket::Input;

// 1. To construct a value (via implicit conversion):
TriageInput input = TriageInput::whole{
    .body = "Crashes on startup",
    .customer_tier = schema::triage_ticket::Input_CustomerTier::kPro,
    .recent_tickets = {{}},  // Nested initializer list
    .subject = "Bug report",
};

// 2. Or with 'auto' (via operator*):
auto input = *TriageInput::whole{
    .body = "Crashes on startup",
    .customer_tier = schema::triage_ticket::Input_CustomerTier::kPro,
    .recent_tickets = {{}},
    .subject = "Bug report",
};
```

#### Rules & Behavior

- **Alphabetical order**: When using designated initializer syntax in C++20, fields must always be specified in alphabetical order (the declaration order in TypePrompt-generated structs).
- **All fields required**: Using `::whole` forces you to set all the fields (including optional fields like `std::optional<T>`, e.g. `.optional_field = std::nullopt` or `.optional_field = value`). Omitting any field in `::whole` results in a compile-time error.
- **Nested initializer lists**: Because fields inside `::whole` are wrapped in `must_init<T>`, initializing a container or struct via initializer list syntax requires double braces (e.g. `{{}}` for an empty vector, or `{{item1, item2}}`).
- **Direct initialization in `Render`**: `Render<Template>({ ... })` accepts `Template::input_type::whole` by default, so passing a designated initializer directly to `Render` automatically enforces that all template input fields are initialized in alphabetical order.

### Discriminated Unions

Union types (like AST trees or multi-variant output nodes) generate type-safe wrapper classes with accessor methods and a `kind()` enum:

```cpp
using PageNode = schema::generate_page_tree::PageNode;

if (node.kind() == PageNode::kind::kSection) {
  const auto& section = node.as_kind_section();
  std::cout << "Section title: " << section.title.value_or("(none)") << "\n";
} else if (node.kind() == PageNode::kind::kHeading) {
  const auto& heading = node.as_kind_heading();
  std::cout << "Heading: " << heading.text << "\n";
}
```

### Multi-Namespace Projects

When your project defines `<namespace>` blocks other than `Main`, templates and schemas are partitioned by namespace:

```cpp
// Render templates from specific namespaces:
auto fin_prompt = Render<templates::Finance::SummarizeTransaction>({
    .amount = {
        .currency = schema::Finance::shared::Currency::kUsd,
        .value = 150.0,
    },
    .category = schema::Finance::summarize_transaction::Input_Category::kExpense,
    .date = "2026-08-01",
    .description = "Cloud server bill",
});

auto legal_prompt = Render<templates::Legal::DraftNda>({
    .disclosing_party = {
        .jurisdiction = "CA",
        .name = "Acme Corp",
        .role = ...,
    },
    .duration_years = 3,
    .purpose_of_disclosure = "M&A evaluation",
    .receiving_party = {
        .jurisdiction = "DE",
        .name = "Beta LLC",
        .role = ... ,
    },
});
```

## Dynamic Template Overrides

TypePrompt supports loading and overriding templates at runtime without recompiling:

```cpp
// 1. Export the template signature and bundle
JsonNode data = TemplateOverrider::templatesData();

// 2. Apply dynamic template overrides (validates signature match)
Result<Templates> overridden = TemplateOverrider::applyOverrides(updated_json_node);

if (overridden.ok()) {
  auto dynamic_prompt = Render<templates::Translate>(
      { .target_language = "French", .text = "Hello" },
      *overridden
  );
}
```

## End-to-End OpenAI / LLM Example

Here is a complete, production-ready example defining a generic `ExecutePrompt` function integrating TypePrompt with an LLM chat completion API:

```cpp
#include "gen/prompts.h"
#include <iostream>
#include <string>
#include <vector>

using namespace typeprompt;

// 1. Wire an execution runner to your LLM API client
template <typename Template, typename Client>
Result<typename Template::output_type> ExecutePrompt(
    Client& client,
    const Prompt& prompt,
    ToolExecutor& tool_executor) {

  // Prepare initial message history
  std::vector<ChatMessage> messages;
  messages.push_back({ .role = "system", .content = prompt.system_message });

  for (const auto& example : prompt.examples) {
    messages.push_back({ .role = "user",      .content = example.user_message });
    messages.push_back({ .role = "assistant", .content = example.response });
  }

  messages.push_back({ .role = "user", .content = prompt.user_message });

  // Conversation and tool execution loop
  while (true) {
    ChatResponse response = client.CreateChatCompletion({
        .model = prompt.meta.model.value_or("gpt-4o"),
        .temperature = prompt.meta.temperature.value_or(0.2),
        .messages = messages,
        .tools = prompt.tools,
        .response_format_json_schema = prompt.output_json_schema,
    });

    if (!response.ok()) {
      return Error("LLM API call failed: " + response.error_message());
    }

    // Check if the LLM produced tool calls
    if (!response.tool_calls().empty()) {
      for (const auto& raw_call : response.tool_calls()) {
        ToolCall call{
            .call_id = raw_call.id,
            .tool_name = raw_call.function_name,
            .stringified_input = raw_call.arguments_json,
        };

        ToolCallResponse tool_resp = tool_executor.Execute(call);

        messages.push_back({
            .role = "tool",
            .tool_call_id = tool_resp.call_id,
            .content = tool_resp.stringified_output,
        });
      }
      continue; // Continue loop to send tool responses back to the LLM
    }

    // Final text response received: parse and validate into typed output
    return ParseResponse<Template>(response.content());
  }
}

// 2. Concrete application usage
int main() {
  using Template = templates::ResearchQuestion;

  // 1. Render prompt with strongly-typed input
  auto prompt = Render<Template>({
      .question = "What is TypePrompt?",
  });

  // 2. Create tool executor
  ResearchExecutor research_executor;
  auto tool_executor = MakeToolExecutor<Template>(&research_executor);

  // 3. Execute prompt with your client
  ApiClient client;
  Result<Template::output_type> result =
      ExecutePrompt<Template>(client, prompt, *tool_executor);

  if (result.ok()) {
    std::cout << "Answer:  " << result->answer << "\n";
    for (const auto& source : result->sources) {
      std::cout << "Source:  " << source << "\n";
    }
  } else {
    std::cerr << "Error: " << result.error().message << "\n";
    return 1;
  }

  return 0;
}
```
